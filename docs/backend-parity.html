Schema work needed

Two rules before writing any migration.
1 · ddl-auto=validate — Hibernate creates and alters nothing. An entity field without its column does not fail at query time, it fails application startup. The migration must ship in the same commit as the entity change.
2 · Every schema change lands twice. The running backend points at the legacy MySQL DQS database, while the QuoteCenter Azure SQL baseline is a parallel track under Documents/QuoteCenter/azure-sql/ (V001__initial_schema.sql, V002__legacy_reference_data.sql — 13 countries, 61 clubs, 61 settings, 6 statuses — plus MigrationRunner.java which applies V001–V003 automatically). Each change from B6, B7, B8, B11 and B16 needs a legacy MySQL migration and a new Azure V00x, or the two schemas silently diverge before cutover. Memberships, prices and inventory were deliberately excluded from V002 because they stay API-owned — keep it that way.

Coordination rules

Adding fields to existing responses

Add new fields as nullable — the frontend handles missing fields gracefully and shows —. Do not remove or rename existing response fields without a frontend PR coordinated first.

Naming conventions

English camelCase in all JSON responses. Legacy DB column names (snake_case) stay in SQL only. Do not leak DB column names into the API contract.

Endpoint pattern

Follow the existing pattern: @RequestMapping("/api/v1/..."), JdbcTemplate queries, no ORM, explicit SQL. New services go in src/main/java/.../service/.

Auth dependency chain

B1 (auth) must ship before B5 (ClubCapabilities), B10 (member panel), and B14 (move-to-frontdesk) — all require a valid role_id from the JWT.

V003 migration — apply first

V003__quotation_payment_state.sql is already written and must be applied to the local container before building B11. Coordinate with the frontend dev — they cannot test payment state persistence until V003 is live in the shared dev DB.
